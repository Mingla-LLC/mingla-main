canonical record: if it shipped, it has a line here.

**Going-forward format:** when an issue on the Mingla Avengers board reaches Done, ONE entry is
appended at the top of the "Shipped" section:

```

```

Detail (evidence, root cause, test notes) lives in the issue, not here. One line per ship,
newest first, plain English first.

History before 2026-07-19 is archived in full at git tag `pre-avengers-archive`. Entries below
that date are a translated back-fill from the old ORCH/artifact system; old IDs are kept in
parentheses for traceability.

- 2026-08-27 — A CI gate has been blaming pull requests for files they never touched, and — the half nobody knew about — silently letting through the exact thing it exists to forbid. The rule is that per-issue workflow wrappers must not proliferate; the gate enforcing it decided "did this branch add a workflow?" by comparing the branch against main's tip RIGHT NOW instead of against the point the branch was cut from. So anything main deleted after the cut looked like something the branch added. Live cost, measured: nine workflow files reported as added by a branch whose only changes were two chat components, cleared by a rebase that changed no file content — nothing in the branch moved to make it pass. The dangerous half is the opposite direction: because the filter only fires when a path is ABSENT at the base, a branch adding a forbidden wrapper at a path main ALREADY carried was invisible and PASSED, exit 0. Main carried nine such wrappers until #2591 deleted them, which is exactly the window in which a colliding wrapper would have sailed through. The fix is one argument — `git diff A B` becomes `git diff A...B` — and the restraint matters as much as the change: the obvious version, resolving the base to the merge base outright, was MEASURED and rejected, because it also moves the authorization lookup and flips a branch cut before its exception contract landed from green to red while carrying a valid token. Three questions were being answered with one variable; exactly one of them should move. Needs no extra fetching, because the gate already probes merge-base immediately before this diff and fails closed at exit 2 otherwise — verified on a depth-1 shallow clone. Four things worth more than the fix. A test written to prove this could not fail: `/1 added workflow\(s\)/` matches `10 added workflow(s)`, so it passed on reverted code, caught only by EXECUTING the revert. The tester's own suite then failed in CI while passing locally, from two independent causes — it inherited the live pull request's event and went looking for `refs/pull/2701/head` in a throwaway repo, and a fixture hardcoded the branch name `main` where a stock runner defaults to `master`; both reproduced on the laptop rather than by pushing. The sibling suite is green by luck rather than isolation and was reported as such instead of as passing (#2709). And the same base-selection bug was then found in a SECOND gate, the append-only ratchet, which calls main's new entries your deletions and invites you to add a removal token — a false red whose obvious remedy silently weakens a real gate (#2705, two independent reproductions). Also found and NOT fixed here: `git mv` an existing workflow into an `issue-*.yml` name and git calls it a rename, so the additions filter never fires and the wrapper lands green — the same predicate's third blind spot (#2708). - 2026-08-26 — The migration ledger was lying, and it had been hiding a dead cache for two months. Every schema change is supposed to leave a receipt; an audit compares receipts against the files on disk. That audit compared VERSION NUMBERS, and the receipts table is keyed on version alone — so it was wrong in both directions at once. In one direction it invented work: 27 receipts record the timestamp a change was APPLIED rather than its file's version, so 25 real, applied migrations read as BOTH missing files AND orphan receipts. The natural response to "missing" is to stamp it, which would have written 25 duplicate receipts. In the other direction it hid work, and that is the expensive half: six pairs of migration files share a 14-digit version prefix, and since only ONE of a pair can ever hold a receipt, the loser is skipped as "already applied" while the ledger reads perfectly clean. Five of those pairs were harmless. The sixth swallowed the column the discover feed's cache needs. That cache has held ZERO rows since 15 June and has never held one — every discover request has recomputed the entire merged event feed from scratch for two months. Nothing surfaced it because both code paths tolerate the missing column: the read turns Postgres's "no such column" into an ordinary cache miss, and the write never checks its error at all. Identity is now the migration NAME rather than its version, with the sharp edge that a same-version receipt under a DIFFERENT name reconciles nothing — which is precisely the case the first version of this fix got wrong, since matching on name alone masked all six collisions behind their twins' receipts. Also shipped: a `@migration-hold:` token so a deliberately-gated migration reads as a decision instead of a finding that cries wolf every run (deliberately a structured token and not prose-sniffing, because the obvious "DO NOT APPLY" heuristic matches 8 migrations that mean "the orchestrator applies this, not you" and all 8 are applied — a heuristic would have suppressed 8 real migrations from the one tool that catches missing schema); a guard against a seventh collision, grandfathered by name so it cannot absorb a new file; and a superseding migration for the swallowed column, written but deliberately NOT applied, since switching on a two-month-dark cache changes discover-feed staleness and should be a choice rather than a side effect. 22 of 23 unstamped migrations were verified against production and stamped; the 23rd is operator-gated and correctly held. Follow-ups filed: #2672 (apply the swallowed column), #2673 (two production changes with no migration file that ever existed in git). (#2614, #2663)

- 2026-08-26 — Mingla now records every refused ticket purchase and why, which is the question behind the organiser complaints and which nothing in the product could answer. The log had been shipped and was recording NOTHING — not a subset, nothing — and it took five rounds to find out why, because every layer reported success. Four real defects sat in front of the root cause and each is genuinely fixed. The allowlist of refusal reasons was built from the 29 the database can raise and never knew the checkout function's own 39, so the very first live refusal stored as `unknown_token`; patching in the nine that had been OBSERVED still left 29 missing, and deriving from both emitters still missed the SHARED modules, a third source of 113 more. That is three failures of the same mechanism in one sitting, so the mechanism was replaced rather than extended a fourth time: a reason is a short snake_case identifier, so the shape is validated and whatever matches is stored, which means a reason invented next year records by name with no migration and no list — while an email address, a phone number, a sentence and a SQL statement are all provably rejected. The checkout also carried its own second copy of that list and collapsed anything outside it BEFORE the database saw it, so the careful allowlist was unreachable on the only path that matters. The write was then `void`ed and never awaited and the runtime tears the request down when the response returns, so six real refusals fired at the deployed endpoint opened zero database calls; awaiting it, bounded by a 1.5s race so telemetry can never turn a refusal into a hang, produced six calls and still zero rows. THE ROOT CAUSE was in the table from its first commit: foreign keys to events, ticket types and brands, so the log could only record a refusal pointing at rows that still exist — and the refusals most worth recording are precisely the ones that do not. `ticket_type_not_found` and `event_not_found` were structurally unrecordable. The same constraint carried ON DELETE CASCADE, so deleting an event would have erased every record of people failing to buy tickets for it; nobody had hit that only because nothing was ever recorded. A refusal is an OBSERVATION — at this time someone tried to buy this and was told no — and the ids are what the buyer SENT, not claims those rows exist or will continue to, so referential integrity was the wrong model and all three keys are dropped, with the probe asserting their ABSENCE so a later migration that re-adds one fails loudly. What made this cost five rounds is worth more than the fix: `.rpc()` does not throw when the database rejects a call, it RESOLVES with an error object, so the recorder awaited it, discarded the value, and succeeded no matter what happened. Every one of the four fixes was verified against a call that reported success while the row was being rejected. A silent success is a far better disguise than a silent failure, and this repository already had a written note saying these errors are plain objects rather than exceptions. The swallowed error now names itself in the logs, because a decision not to FAIL is not a decision not to TELL ANYONE — that is what finally proved the error was never an exception at all. PROVEN, not asserted: six real refusals fired at the deployed endpoint, six rows recorded, plus four more distinct reasons recorded separately with surface, quantity and dialling code, no phone number or email stored. DELIBERATELY INCOMPLETE and recorded as such: only 6 of 51 refusal exits in the checkout carry a recorder, so headline reasons including `bookings_closed`, `paystack_initialize_failed`, `intake_form_required` and `pricing_config_unavailable` still record nothing.
