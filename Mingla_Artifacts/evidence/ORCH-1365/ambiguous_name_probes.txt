ORCH-1365 INCREMENT — ambiguous country / US-state collision ("atlanta georgia" → 0 results)
Live Mapbox Search Box /suggest probes, 2026-07-12. Non-Lagos / non-US origin (this machine).
Token from master-keys. Endpoint: GET https://api.mapbox.com/search/searchbox/v1/suggest
Params re-verified vs live docs (WebFetch https://docs.mapbox.com/api/search/search-box/ 2026-07-12):
  types   = comma list of {country,region,postcode,district,place,city,locality,neighborhood,
            street,address,poi,category}
  country = comma-separated ISO 3166 alpha-2 codes
  proximity = "ip" OR "longitude,latitude"
  limit   = up to 10 (max 10)
  session_token = REQUIRED
SESSION BILLING (quoted from live docs): "A Search Session is a series of Search API calls
  bundled together for billing purposes." A session ends+bills on: /suggest→/retrieve with a
  common session_token, OR /suggest with no /retrieve within 180s, OR 50 successive /suggest
  with a common token. => MULTIPLE /suggest calls sharing one session_token = ONE billable
  session. THE FALLBACK RETRY REUSES THE SAME session_token => NO EXTRA BILLING, only latency.
TYPES set under test (unchanged from the shipped core) = place,locality,neighborhood,region,district
Script: scratchpad/probe_ambiguous.sh

CONTEXT — the bug (already captured by tester in tester_e2e_edge_handler_live_mapbox.txt line 44):
  handleSuggestPlaces("atlanta georgia") → parseTrailingCountry strips "georgia" → country=ge
  (Georgia the COUNTRY) → q=atlanta&country=ge → Mapbox returns EMPTY → user sees zero results.

STRATEGIES EVALUATED (task):
  A — ZERO-RESULT FALLBACK: run the strip+country-biased call; if it returns 0 suggestions,
      RETRY with the FULL original query (no strip, no country), reusing the session_token.
  B — US-STATE EXCLUSION SET: never strip a token that is also a US state (georgia, ...).
  C — HYBRID (exclusion set + fallback for the long tail).

COLLISION-SET AUDIT (node intersect of the 227-key COUNTRY_NAME_TO_ISO map vs 50 US states):
  Country-map keys that are ALSO US state names: ["georgia"]   <-- the ONLY US-state collision.
  "jordan" is a country key but NOT a US state (given-name/country; single token → never stripped).
  => An exclusion set (B) would carry exactly ONE entry today (georgia) but see R5-tbilisi below.

DECISION — STRATEGY A (zero-result fallback with the FULL original query), justified by evidence:
  1. REQUIREMENT 1: R1-a empty → R1-b Atlanta,Georgia,USA #1. MET.
  2. REQUIREMENT 2: R2-a non-empty → no fallback → lekki-nigeria win preserved byte-for-byte. MET.
  3. REQUIREMENT 3/4: single-call paths unchanged (R3/R4). MET.
  4. REQUIREMENT 5: paris-texas already works (5.2); cordoba disambiguates (5.3); jordan reasonable
     (5.1); AND R5-tbilisi (5.4) proves A serves the genuine-Georgia-country user that B/C cannot.
  5. GENERAL — no exhaustive collision list to maintain: ANY "<place> <country-word>" where the
     place is not in that country (future-proof beyond Georgia) self-corrects.
  6. BUSINESS-SAFE + BILLING-SAFE: fallback lives ONLY inside handleSuggestPlaces (consumer). The
     retry reuses the SAME session_token → Mapbox bills ONE session (docs quoted above). Cost = one
     extra HTTP round-trip, ONLY when the biased first call is empty (rare: over-strip + place-not-
     in-country). The hot path (lekki nigeria, cordoba, single tokens, non-stripped) = ONE call.

WHY NOT B: needs a maintained US-state list (only "georgia" today, but brittle) AND wrongly
  overrides the genuine Georgia-COUNTRY user (R5-tbilisi). WHY NOT C: A already covers B's one case
  AND the long tail with no list; the exclusion set in C is dead weight that reintroduces the
  Tbilisi regression. A is strictly simpler AND strictly more correct.

TRIGGER CONDITION (exact): fallback fires IFF parseTrailingCountry returned a `country` (a strip
  happened) AND the biased first call returned HTTP-ok with ZERO mapped suggestions. On a non-OK
  first call, return the error unchanged (today's contract). Single-call otherwise.
